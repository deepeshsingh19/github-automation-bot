# AI Collaboration Notes

## AI tools and models used

I used ChatGPT throughout the project as an engineering assistant for architecture discussions, implementation, debugging, testing, security review, and deployment troubleshooting. I made the final engineering decisions, manually created and reviewed the project files, ran the tests and builds, configured the external services, and verified the production behavior.

The application uses Google Gemini for AI triage, currently with `gemini-3.5-flash-lite`.

## Key decisions I made

### 1. Durable PostgreSQL event processing

I chose PostgreSQL as the durable source of truth for events and actions instead of relying on an in-memory queue. This allows the system to recover from restarts and transient failures. Events use worker leases, retries, and `FOR UPDATE SKIP LOCKED` so multiple workers cannot safely claim the same work.

### 2. GitHub App for repository automation

I chose a GitHub App rather than using a user's OAuth token for GitHub write operations. User login and GitHub App installation are separate concerns, while installation tokens are used for repository automation.

### 3. Persistent worker deployment

I chose a persistent Node.js service on Render instead of a serverless-only worker. Webhooks are persisted first, then processed asynchronously by the worker, with the sweep endpoint acting as an additional recovery mechanism.

## Hardest wrong turn: manual retry re-ran successful actions

**What the AI got wrong.** The first retry design reset every action on an event back to `PENDING` when the user clicked Retry.

**How I noticed.** I checked the design against one invariant: a successful side effect must never run twice. I traced an event with two successful actions and one failed Slack action. Retrying the event would have executed the already-successful GitHub actions again.

**Fix.** Retry now resets only failed actions, while also resetting the event's retry state. The update is guarded by the failed status and ownership checks, and is performed transactionally. This preserves successful actions while allowing failed work to run again.

I also added the retry behavior to the test coverage so successful actions remain untouched.

## Other important issues caught during development

* The initial claim design released database locks before processing the claimed events. It was replaced with a single `UPDATE ... RETURNING` claim using `FOR UPDATE SKIP LOCKED` and stale-lock recovery.
* A uniqueness design based on `(eventId, ruleId, type)` was insufficient when a rule contained multiple actions and when `ruleId` was `NULL`. This was replaced with deterministic `actionKey` values.
* A polling worker was initially designed inside serverless Next.js. That was changed to a persistent Node.js worker because serverless processes cannot be treated as long-running workers.
* The webhook ingestor initially accepted every `issues` action, including events generated by the bot's own label changes. This could create automation loops, so event actions are now explicitly allowlisted.
* The login flow initially handled `searchParams` incorrectly for the current Next.js API, which caused `installation_id` to be lost. There were also TypeScript issues around the GitHub profile shape and a pagination implementation that could have followed an arbitrary `Link` URL with the user's token.
* Repository connection initially used an `upsert` pattern that could potentially re-point another user's repository row during a race. It was replaced with ownership-scoped update/create logic and unique-conflict handling.
* During production testing, GitHub webhooks were still pointing to a Smee development endpoint. Local testing worked, but stopping the local process meant production events were no longer reaching Render. I found this by checking GitHub delivery history and changed the production webhook to the Render endpoint.
* Gemini also had an intermittent production failure during testing. The initial model was unavailable for the account, so it was changed to `gemini-3.5-flash-lite`. A later intermittent timeout led to a bounded retry for transient AI/network failures rather than simply increasing the timeout.

## Known limits

* Delivery is at-least-once. A crash between an external side effect and marking the action successful can still cause duplication. GitHub comments use an internal marker to detect an already-created comment, while Slack can still duplicate in that narrow window.
* Render's free tier can sleep, and a webhook delivery that times out is not automatically replayed by GitHub. The application has a sweep mechanism, but a dedicated redelivery/reconciliation mechanism would make this stronger.
* Installation ownership currently follows a first-claimer model, with repository permission checks providing an additional safeguard at connection time.

## With more time

I would add delivery-history reconciliation so missed GitHub events can be recovered automatically, structured logs keyed by delivery ID, a richer failure/retry history view, encryption-key versioning, and a full end-to-end test against a real GitHub App and webhook proxy.
